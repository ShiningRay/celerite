## Data-driven conclusions

1. **Startup dominates CLI scenarios** (10× delta). Celerite's single-binary
   launch is already optimal for the hot CLI path; no further startup work is
   planned. Fiber concurrency tuning would not move this number.
2. **Bridge allocations are bounded and small** (13k objects ≈ single-digit ms
   of Ruby GC work) per Gemfile evaluation — they do not justify pre-warming
   or persistent bridge processes yet. Revisit only if Gemfile evaluations
   appear hot in a real-workload profile.
3. **The reference lock is allocation-heavy** (~123k objects); celerite's
   native path has no equivalent cost. This is the main structural win and
   matches the wall-time deltas in
   [results-2026-11-07.md](results-2026-11-07.md).
4. **IO is minimal with incremental index updates** — ETag/Range means cold
   caches stay tiny for incremental sources. No I/O optimization needed at
   fixture scale; revisit with a full rubygems.org `/versions` (~10 MB) in a
   networked benchmark.
5. **Peak-memory metric deferred**: the inherited-environment duplicate-key
   issue (NO_PROXY/no_proxy case mismatch) breaks PowerShell Start-Process
   measurement. Tracked as a tooling limitation; unix CI (GitHub Actions
   ubuntu-latest) can measure with `/usr/bin/time -f %M` instead.
