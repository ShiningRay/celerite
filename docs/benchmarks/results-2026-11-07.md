# Benchmark results — 2026-11-07

Environment: Windows x64 (win32 10.0.26300), Crystal 1.22.1 (MSYS2 GNU target),
Ruby 4.0.6 x64-mingw-ucrt, reference Bundler 4.0.24, local NVMe SSD, fixture
index (json_pure 2.6.0/2.8.1, racc 1.8.1, thor 1.3.2) on `file://`.

Method: `script/benchmark 3` — mean wall time over 3 runs per scenario,
fresh sandbox per cold run, isolated HOME/GEM_HOME/BUNDLE_PATH per run.
Raw numbers are reproducible via the script; no marketing rounding.

| Scenario | Reference (ms) | Celerite (ms) | Ratio |
|---|---|---|---|
| cold lock (fresh index cache) | 1214 | 658 | 1.85× faster |
| hot lock (warm cache re-lock) | 1176 | 584 | 2.01× faster |
| no-change lock (locked reuse) | 1199 | 649 | 1.85× faster |
| install (download + unpack) | 4966 | 657 | 7.56× faster |
| no-change install (idempotent) | 5309 | 659 | 8.06× faster |

## Interpretation notes

- The reference spends most of its wall time in Ruby interpreter startup and
  gem activation (~1.1s baseline) even for no-op scenarios; Celerite's native
  binary avoids that fixed cost. The no-change install delta is dominated by
  the reference re-verifying installed gems through RubyGems APIs.
- The install comparison (7.6×) reflects racc's native extension build: the
  reference builds extensions through RubyGems' full install pipeline on every
  cold install; Celerite shells out through the bridge only for the build step.
  Both produce functionally equivalent trees (differential-verified).
- These numbers are a single-machine snapshot, not a claim about all
  environments. Re-run `script/benchmark` on your hardware before quoting.
- Roadmap M6 forbids trading correctness for speed: all scenarios above run
  with checksum verification enabled and differential-verified outputs.
