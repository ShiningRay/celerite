# Upgrade, uninstall, and cache maintenance (M6)

## Upgrading Celerite

1. Build/install the new version (`shards build` produces `bin/celerite`, or
   replace the installed binary).
2. Nothing else is required: caches and lockfiles are forward-compatible.
   - The download cache (`~/.bundle/cache/downloads/`) is content-addressed by
     name/version/platform; new versions simply add entries.
   - The compact-index cache (`~/.bundle/cache/compact_index/`) is keyed per
     remote and updated via ETag/Range; old entries stay valid.
3. Verify after upgrade: `celerite version` then `celerite check` in any
   active project. Lockfiles are not rewritten by an upgrade (M1 read-only
   guarantee holds across versions).

## Uninstalling Celerite

Celerite never modifies state outside these locations:

| Location | Content | Safe to delete? |
|---|---|---|
| `bin/celerite` (or the installed binary) | the executable | yes — removes Celerite only |
| `~/.bundle/cache/downloads/` | downloaded `.gem` files | yes — re-downloaded on demand |
| `~/.bundle/cache/compact_index/` | index caches | yes — re-fetched on demand |
| `<bundle_path>/ruby/<abi>/…` | installed gems (shared with the reference Bundler layout) | deleting removes gems for **both** tools; use `bundle install` afterwards to restore |
| project `.bundle/config` | local config | yes — but the reference Bundler also reads it |

Your project `Gemfile`/`Gemfile.lock` are never touched by uninstalling: they
are plain files owned by your repository.

## Rolling back to the reference Bundler

1. Delete the shim if you installed `script/bundle` onto PATH (Celerite is
   opt-in and never replaces `bundle` by itself).
2. Run `bundle install` once with the reference Bundler; it reuses the same
   installed tree layout and regenerates any lockfile sections Celerite did
   not emit (e.g. per-profile CHECKSUMS) exactly as upstream would.
3. No project file changes are required — lockfiles generated by Celerite are
   byte-compatible with the pinned reference profiles (differential-verified).

## Cache maintenance

- `celerite clean` prunes installed gems not in the current bundle's lockfile
  (reference-parity output).
- The download cache is self-limiting per project usage; a full reset is safe:
  `rm -rf ~/.bundle/cache/downloads ~/.bundle/cache/compact_index`.
- Corrupted cache entries (partial downloads, checksum failures) are never
  published — the atomic write pipeline removes temp files on failure and a
  checksum mismatch deletes the cached artifact before re-downloading.

## Diagnostics

- `CELERITE_DEBUG_RESOLVER=1` traces solver decisions (package selection,
  derivations, conflicts).
- `CELERITE_BRIDGE_SERVER` points at an alternate bridge script (tests).
- `CELERITE_REFERENCE_BUNDLER_LIB` pins the compatibility profile's Bundler
  load path (set automatically by `script/differential`).
- `CELERITE_PROFILE_BUNDLER_VERSION` selects the serialization profile
  (4.0.24 vs 2.7.2 differences: CHECKSUMS defaults, `BUNDLED WITH` indent).
- Exit codes are documented in `docs/compat-matrix/cli-commands.md` and match
  the reference (`check` 1, `SolveFailure` 6, `GemNotFound` 7, …).
